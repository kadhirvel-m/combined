The "Moving Box"
Paradox

Imagine a filing cabinet. To use it, you must have the right folder, in the right alphabetical order, with papers cut to the exact size. That is Structured Data (SQL).

Now imagine a Moving Box. You can throw in a book, a lamp, or even a smaller box inside it. The only rule? You must write on the outside what is on the inside. This is Semi-Structured Data.

Structured

Rigid. Like a spreadsheet. If you want to add a phone number, every single row needs a phone number column.

Semi-Structured

Flexible. Self-describing. One person has a phone number, the next has an email, the third has a list of pets.

The Engineering Reality

Self-Describing Data

Remember the labels on your items? In computer science, this is the Key-Value Pair. Unlike a database table that stores just the value ("John"), semi-structured data stores the meaning with the data ("name": "John"). This allows different documents to have completely different fields.

Common Formats

  • JSON The web standard
  • XML Tag based (Old School)
  • BSON Binary JSON (MongoDB)

Nesting & Hierarchy

Just like putting a small box inside a big box, semi-structured data supports Nesting. You can have a list inside an object inside a list. SQL struggles with this; NoSQL thrives on it.

The Trade-Off

PROS

Agility. You can change your app's data structure without taking down the database. Great for Big Data and rapid prototyping.

CONS

Data Integrity. Since there are no rules, data can get messy. Queries can be slower if the nesting is too deep.
